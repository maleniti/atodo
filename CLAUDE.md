# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A standalone to-do list web app (recurring tasks, overdue/failed states, work timers), ported out of the `browser` project's new-tab widget. Plain HTML/CSS/JS, no build step, no framework, no package.json. Data lives entirely in `localStorage` — there is no backend. Also includes a marketing/subscription flow (`landing.html` and friends, see Architecture) alongside the app itself.

## Commands

- **Run the app**: open `index.html` directly in a browser, or serve the directory (e.g. `npx serve .`). There's no dev server or build step.
- **Run tests**: `node recurrence.test.js` — a plain Node script using `node:assert`, not a test framework (no jest/mocha). It exits non-zero and throws on the first failed assertion; there's no way to run a single test in isolation, just re-run the whole file. Prints `recurrence.test.js: all assertions passed` on success.
- **Docker**: `docker build .` copies the static files (see the two `COPY` lines in `Dockerfile` — the main app's scripts, and the landing/checkout/success/cancel pages) into an `nginx:alpine` image. If you add a new source file, add it to one of those `COPY` lines too, or it won't ship. `config.js` is the one deliberate exception — see Configuration below. `./atd <port>` builds and (re)runs the image via Docker; it requires a `.env` file in this directory (refuses to start without one) and sources it with `set -a` before `docker run`, so anything in `.env` (`UNSPLASH_ACCESS_KEY`, `LANDING_VIDEO_URL`) is forwarded into the container as an env var.

## Configuration

Two configurable values so far, both loaded from `window.APP_CONFIG` set in `config.js`. There's no build step, so this is a plain untracked (gitignored) JS file, not an env-driven bundler define:

- An app-wide Unsplash Access Key (used by the background picker in Settings — see `app.js`'s `configuredUnsplashAccessKey`/`loadUnsplashAccessKey`).
- `landingVideoUrl`, a YouTube link for `landing.html`'s walkthrough video (see `landing.js`'s `toYouTubeEmbedUrl`, which accepts a plain watch URL, a `youtu.be` short link, or an already-embeddable one). Left empty, that page shows a placeholder instead.

- **Local dev**: copy `config.example.js` to `config.js` and fill in real values (get an Unsplash key at https://unsplash.com/developers). `index.html`/`landing.html` load `config.js` before their other scripts; it's fine to skip this file entirely (`config.js` 404s harmlessly, `window.APP_CONFIG` stays undefined) — the background picker then falls back to asking each user to paste in their own key, stored per-device in `localStorage`, and the landing page just shows its video placeholder.
- **Docker (via `./atd`)**: don't create `config.js` yourself — put `UNSPLASH_ACCESS_KEY=...`/`LANDING_VIDEO_URL=...` in a gitignored `.env` file next to `Dockerfile` instead. `./atd` sources it and forwards both into the container; `docker-entrypoint.d/40-write-app-config.sh` (nginx:alpine's image runs every `*.sh` in `/docker-entrypoint.d/` on container start) then generates `config.js` fresh from those env vars every time the container starts, so either can be rotated by editing `.env` and re-running `./atd`, no rebuild needed.

## Architecture

Two independent halves sharing one origin (and so one `localStorage`): the to-do app itself (`index.html`), and a marketing/subscription/legal flow (`landing.html`, `checkout.html`, `success.html`, `cancel.html`, `privacy.html`, `terms.html`) that isn't part of that SPA and never loads `app.js` (which assumes `index.html`'s own DOM exists and would throw trying to query it elsewhere). No modules, no bundler anywhere — load order matters and everything each page loads is global.

**The app** — five scripts, loaded via plain `<script>` tags in this order (`index.html`): `sharedInputBehavior.js`, `recurrence.js`, `auth.js`, `app.js` (plus `config.js` first, see Configuration).

- **`recurrence.js`** — pure recurrence/overdue date math, no DOM or localStorage access. UMD-lite: exports via `module.exports` under Node (so `recurrence.test.js` can require it directly) and `window.Recurrence` in the browser. This is the only file with a test suite, and the only one that's meaningfully unit-testable in isolation — `app.js` is DOM-driven and untested. When changing recurrence/due-date logic, add assertions to `recurrence.test.js` in the same style as the existing ones (plain `assert.ok`/`assert.strictEqual` with a descriptive message as the last arg).
- **`auth.js`** — account/token/subscription storage primitives (`uid`, `loadUsers`/`saveUsers`, `mintToken`/`decodeToken`, `describeSubscription`, `startTrialSubscription`/`startPaidSubscription`/`cancelSubscription`, `getCurrentUserIdFromStoredToken`). Pulled out of `app.js` specifically so `landing.html`/`checkout.html` can use the same account/subscription logic without loading the whole SPA script. No DOM beyond `localStorage`, same spirit as `recurrence.js`.
- **`app.js`** — everything else: task CRUD, the to-do list rendering/state machine, timers, the generic `showFormModal()` used for all add/edit forms (a `window.prompt()`/native-dialog replacement, since Linux Chromium has no OS text-input dialog), the recurring-task edit/delete "split" logic (`applySplitEdit`/`applySplitDelete`), and the free-tier subscription limits (see Key domain concepts below). One large file with heavy comments explaining *why*, not what — read the comments before changing behavior near timers, dismissal, or the recurrence split logic; the invariants are non-obvious and are explained inline rather than in a design doc.
- **`sharedInputBehavior.js`** — document-delegated focus/click/double-click text-selection behavior for every text `<input>`/`<textarea>` on the page, including ones created dynamically by modals. Self-contained IIFE, no exports.

**The marketing/subscription flow** — separate static pages, own stylesheet (`landing.css`, deliberately not `style.css`: that one assumes the app's fixed-viewport, no-page-scroll SPA layout, which would break these pages' normal scrolling), own EN/HR i18n (`site-i18n.js`) entirely separate from `app.js`'s own i18n system (different storage, different dictionary shape — see below):

- **`site-i18n.js`** — this flow's language handling: `resolveInitialSiteLanguage()` (a `?lang=` URL handoff, else a stored preference, else IP geolocation, same country-code rule as `app.js`'s own detection), `applySiteTranslations()` (a `data-i18n`/`data-i18n-html` sweep, same split as `app.js`'s `applyStaticTranslations`), and `initSitePage(dict, onLanguageChange?)` that every other page in this flow calls once with its own `{ en: {...}, hr: {...} }` dictionary. Also auto-updates every `a.js-login-link`'s `?lang=` query param on each render, so a link into `index.html` (the login/register screen, which has its own separate i18n) opens in the same language — see `boot()`'s own handling of that param in `app.js`.
- **`landing.html`**/**`landing.js`** — video + feature/pricing marketing page. Its pricing buttons check `getCurrentUserIdFromStoredToken()` (`auth.js`): logged in goes straight to `checkout.html?plan=...`, logged out goes to `index.html?next=checkout&plan=...&lang=...` first (see `app.js`'s login-form submit handler and `boot()`, both of which continue on to checkout right after if `next` is set).
- **`checkout.html`**/**`checkout.js`** — mocked "processing payment" page standing in for a real Stripe Checkout round trip (create session → redirect to Stripe → Stripe redirects back) that doesn't exist yet, Stripe integration being backend work for later. `pollPaymentStatus()` is shaped like a real status poll but just resolves after a couple of intervals; swap its body, not its callers, once a real endpoint exists. Grants the subscription client-side via `startPaidSubscription` once "confirmed", then redirects to `success.html`.
- **`success.html`**/**`success.js`**, **`cancel.html`**/**`cancel.js`** — the mock stand-ins for Stripe's `success_url`/`cancel_url` redirect targets; only `site-i18n.js` for logic, nothing else to do once there.
- **`privacy.html`**/**`privacy.js`**, **`terms.html`**/**`terms.js`** — the Privacy Policy/Terms of Service, one `data-i18n-html` key per numbered section (heading + body together) rather than per-sentence, since that's far easier to keep aligned between languages for a document this size. Linked from the footer of every page in this flow, from below the login/register form on `index.html` (`.auth-legal-links`), and from the account menu once logged into the app (see `menu-item`s in `index.html`'s `#user-menu-dropdown`, right before Log out) — all three entry points are meant to open in whichever language is currently active where the link was clicked from (see `site-i18n.js`'s comment and `app.js`'s `updateOutboundLegalLinks`).

### Key domain concepts (in `app.js`)

- **Task model**: `{ id, name, description, dueDate, dueTime, allDay, appointment, endDate, frequency, completions: {dateISO: true}, dismissed: {dateISO: true}, timer? }`. `frequency` shapes are documented at the top of `recurrence.js` (`once`/`days`/`weeks`/`months`, with weekly weekday lists and several monthly day-selection modes).
- **Overdue vs. failed**: a normal task that's missed becomes "overdue" and carries over; a task flagged `appointment` becomes "failed" (permanent, crossed out red) instead once past due — see `pastDueStatus()`.
- **Dismissal**: `task.dismissed` (separate from `task.completions`) tracks whether a past occurrence should still show on the list, so a failed appointment's history isn't rewritten to look completed just to declutter the view. Completing a carried-over item lingers ~5s before dismissing (`scheduleDismissal`) so the checkmark is visible before it disappears.
- **Active task / timers**: only one task can be "active" at a time (`activeTaskId`), always changed through `setActiveTaskId()` so a timer's running/paused state is checkpointed consistently. A timer's remaining time is derived from a fixed checkpoint plus elapsed wall-clock time (`currentTimerRemaining`), not a live countdown, so it survives page reloads without drift.
- **Recurring task edits/deletes**: double-clicking a recurring occurrence prompts for scope (`showEditScopeChoice`: this occurrence / this and following / all). Non-"all" scopes split the series into new task records rather than mutating in place — see the extensive comments on `applySplitEdit`/`applySplitDelete`.
- **Three list views**, cycled via one toggle button and persisted separately from the underlying overdue/active computations (view mode is a display preference only): "pending/overdue" (`computeTodoDisplayItems`) shows every overdue/failed occurrence since the start of the current calendar month plus today/tomorrow, ignoring `task.dismissed`; "next recurrence" (`computeNextRecurrenceItems`) is the day-to-day decluttered view that respects dismissal; "all tasks" (`computeAllTasksItems`) lists every occurrence in the current calendar month regardless of state.
- **Subscriptions & free-tier limits**: a free/lapsed account is capped at `FREE_TASK_LIMITS.once`/`.recurring` tasks and `NOTES_PER_TASK_LIMIT` notes per task, counted by `task.taskId` (not `task.id`, which changes across a recurring split — see `unlockedTaskIds`/`canCompleteOrNoteTask`). A lapsed subscription keeps every task/note but only grandfathers the first ones ever created (by `task.createdAt`); a task beyond that shows a padlock in place of its checkbox/Add note button/Manage Tasks row instead. Free/lapsed accounts also get a permanent, unremovable `SUBSCRIPTION_PROMPT_TASK_ID` task (see `ensureSubscriptionPromptTask`/`isProtectedTask`). The bearer token embeds a subscription snapshot (see `auth.js`'s `mintToken`) so limit checks read from the token rather than a freely-editable place; `subscribeCurrentUserToTrial`/`cancelCurrentUserSubscription` in `app.js` re-mint it after a change.
- **Account deletion & inactivity**: a user can permanently delete their own account from Settings' danger zone (`deleteCurrentUserAccount`); an account untouched for 12 months (`auth.js`'s `INACTIVITY_LIMIT_MS`) is deleted automatically instead, per the Privacy Policy. Both funnel through `wipeAccountData(userId)`, which removes the `users` row and clears every shared storage key tasks/profile/etc. live in (see that function's own SHORTCUT comment on why "this account's data" currently means the *whole* shared blob, not a scoped subset). The inactivity check lives in `getMe()` — the one chokepoint both `boot()`'s existing-token path and a fresh `login()` always call through — rather than in `login()` itself, so a stale/deleted account can't slip past either entry point (see `getMe`'s own comment for why). `auth.js`'s `recordUserActivity`/`isUserInactive` track `lastActiveAt` (touched on every resumed session) separately from `lastLoginAt` (touched only by a fresh password login) specifically so a long-lived token that keeps getting reused doesn't get wrongly treated as abandoned.
