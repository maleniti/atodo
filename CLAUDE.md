# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A to-do list web app (recurring tasks, overdue/failed states, work timers), ported out of the `browser` project's new-tab widget. Plain HTML/CSS/JS, no build step, no framework, no package.json. Multi-tenant: every account's tasks/profile/subscription live server-side behind a real HTTP backend, not in `localStorage` — see `api-spec.yaml` for the full contract and Architecture below for how the client talks to it. `localStorage` is only used client-side now for the bearer token itself and (briefly, pre-login) marketing-language/config values. Also includes a marketing/subscription flow (`landing.html` and friends, see Architecture) alongside the app itself.

There is no backend implementation in this repository — `api-spec.yaml` is the contract a separate backend project is expected to implement; this repo is just the client.

## Commands

- **Run the app**: needs a backend implementing `api-spec.yaml` reachable at the configured `apiBaseUrl` (see Configuration below) — open `index.html` directly in a browser, or serve the directory (e.g. `npx serve .`), either way there's no dev server or build step for the client itself.
- **Run tests**: `node recurrence.test.js` and `node occurrence.test.js` — plain Node scripts using `node:assert`, not a test framework (no jest/mocha). Each exits non-zero and throws on the first failed assertion; there's no way to run a single test in isolation, just re-run the whole file. Prints `<file>: all assertions passed` on success. Both are pure logic with no I/O (date math and task/occurrence-merge math respectively) — the rest of the client (`app.js`, `auth.js`, `checkout.js`) has no automated test coverage; verify changes there by hand against a running backend.
- **Docker**: `docker build .` copies the static files (see the two `COPY` lines in `Dockerfile` — the main app's scripts, and the landing/checkout/success/cancel pages) into an `nginx:alpine` image. If you add a new source file, add it to one of those `COPY` lines too, or it won't ship. `config.js` is the one deliberate exception — see Configuration below. `nginx.conf` replaces the image's stock `default.conf` only to add `Cache-Control: no-cache`, so a redeploy is picked up on the next plain reload rather than a hard reload (see its own comment for why stale client code matters here). `./atd <port>` builds and (re)runs the image via Docker; it requires a `.env` file in this directory (refuses to start without one) and sources it with `set -a` before `docker run`, so anything in `.env` (`UNSPLASH_ACCESS_KEY`, `LANDING_VIDEO_URL_EN`, `LANDING_VIDEO_URL_HR`, `API_BASE_URL`) is forwarded into the container as an env var. This container only ever serves the static client — the backend is a separate deployment.

## Configuration

Four configurable values so far, all loaded from `window.APP_CONFIG` set in `config.js`. There's no build step, so this is a plain untracked (gitignored) JS file, not an env-driven bundler define:

- `apiBaseUrl`, the backend implementing `api-spec.yaml` (e.g. `https://api.example.com`) — `auth.js`'s `apiFetch` prefixes every request with `${apiBaseUrl}/atodo/v1`. Left empty, requests go to a same-origin `/atodo/v1`, which only works if the backend happens to be reverse-proxied onto this same origin.
- An app-wide Unsplash Access Key (used by the background picker in Settings — see `app.js`'s `configuredUnsplashAccessKey`/`loadUnsplashAccessKey`).
- `landingVideoUrlEn`/`landingVideoUrlHr`, YouTube links for `landing.html`'s walkthrough video — one per language, since each is a separate recording rather than one video with translated captions (see `landing.js`'s `setUpVideo`, which re-picks and re-embeds on load and on every EN/HR toggle click via `site-i18n.js`'s `initSitePage`, and `toYouTubeEmbedUrl`, which accepts a plain watch URL, a `youtu.be` short link, or an already-embeddable one). Either left empty independently, that language just shows a placeholder instead.

- **Local dev**: copy `config.example.js` to `config.js` and fill in real values (get an Unsplash key at https://unsplash.com/developers). `index.html`/`landing.html` load `config.js` before their other scripts; it's fine to skip this file entirely (`config.js` 404s harmlessly, `window.APP_CONFIG` stays undefined) — `apiBaseUrl` then falls back to a same-origin `/atodo/v1`, the background picker falls back to asking each user to paste in their own key (stored per-device in `localStorage`), and the landing page just shows its video placeholder regardless of language.
- **Docker (via `./atd`)**: don't create `config.js` yourself — put `UNSPLASH_ACCESS_KEY=...`/`LANDING_VIDEO_URL_EN=...`/`LANDING_VIDEO_URL_HR=...`/`API_BASE_URL=...` in a gitignored `.env` file next to `Dockerfile` instead. `./atd` sources it and forwards all four into the container; `docker-entrypoint.d/40-write-app-config.sh` (nginx:alpine's image runs every `*.sh` in `/docker-entrypoint.d/` on container start) then generates `config.js` fresh from those env vars every time the container starts, so any of them can be rotated by editing `.env` and re-running `./atd`, no rebuild needed.

## Architecture

Two independent halves sharing one origin (and so one `localStorage`, used now only for the bearer token and a couple of pre-login display preferences — see Configuration/`site-i18n.js` below): the to-do app itself (`index.html`), and a marketing/subscription/legal flow (`landing.html`, `checkout.html`, `success.html`, `cancel.html`, `privacy.html`, `terms.html`) that isn't part of that SPA and never loads `app.js` (which assumes `index.html`'s own DOM exists and would throw trying to query it elsewhere). Both halves talk to the same backend (`api-spec.yaml`, `/atodo/v1`) via `auth.js`. No modules, no bundler anywhere — load order matters and everything each page loads is global.

**The app** — six scripts, loaded via plain `<script>` tags in this order (`index.html`): `sharedInputBehavior.js`, `recurrence.js`, `occurrence.js`, `auth.js`, `app.js` (plus `config.js` first, see Configuration).

- **`recurrence.js`** — pure recurrence/overdue date math, no DOM or network access. UMD-lite: exports via `module.exports` under Node (so `recurrence.test.js` can require it directly) and `window.Recurrence` in the browser. Answers "does this pattern (dueDate/frequency/endDate) land on date X" and related next/previous-occurrence questions; knows nothing about `tasks`/`occurrences` themselves. When changing recurrence/due-date logic, add assertions to `recurrence.test.js` in the same style as the existing ones (plain `assert.ok`/`assert.strictEqual` with a descriptive message as the last arg).
- **`occurrence.js`** — the pure counterpart for the Task/Occurrence data model itself (see Key domain concepts below): finding/creating an Occurrence row, applying a `recurUntilCompleted` occurrence's own chain into a shape `recurrence.js` can consume (`recurrenceShim`), applying a "this occurrence only" edit's field overrides, and pooling notes across Task/Occurrence for the free-tier note limit. Same UMD-lite/no-DOM pattern as `recurrence.js`, with its own `occurrence.test.js`. Together, these two files are the only ones meaningfully unit-testable in isolation — `app.js` is DOM-driven and untested.
- **`auth.js`** — the API client. `apiFetch(path, { method, body, token })` is the one place every request to the backend goes through: prefixes `path` with `apiBaseUrl` + `/atodo/v1` (see Configuration), attaches the bearer token from `localStorage` (or an explicitly-passed one, for a token that isn't stored yet — see `getMe`'s own call sites in `app.js`), and turns any non-2xx response into a `codeError(code, message)` so the rest of the app can branch on a stable `err.code` the same way regardless of which endpoint failed. Everything else here is a thin wrapper around one `api-spec.yaml` endpoint (`startTrialSubscription`, `createCheckoutSession`/`getCheckoutSessionStatus`, `cancelSubscription`, `scheduleAccountDeletion`/`cancelScheduledAccountDeletion`) plus `uid()` (still-client-generated task ids, see api-spec.yaml's `PUT /tasks`), `decodeToken()`/`describeSubscription()` (non-authoritative local reads of a token's claims, for instant UI decisions that don't need a round trip), and `getCurrentUserIdFromStoredToken()`. Pulled out of `app.js` specifically so `landing.html`/`checkout.html` can use the same API client without loading the whole SPA script. No DOM beyond `localStorage`, same spirit as `recurrence.js`.
- **`app.js`** — everything else: task CRUD, the to-do list rendering/state machine, timers, the generic `showFormModal()` used for all add/edit forms (a `window.prompt()`/native-dialog replacement, since Linux Chromium has no OS text-input dialog), the recurring-task edit/delete "split" logic (`applySplitEdit`/`applySplitDelete`), and the free-tier subscription limits (see Key domain concepts below). Its own auth/profile/task functions (`registerUser`, `login`, `getMe`, `loadTasks`/`saveTasks`, `saveUserProfile`, ...) are thin `apiFetch` calls into `auth.js`'s client; most of them are fire-and-forget (errors only `console.error`'d) except `saveTasks()`, whose failures are surfaced: its `PUT /tasks` writes are serialized (one in flight, later changes folded into the next request), and a failed one stays queued behind a visible "not saved" banner with automatic retries and a leave-page prompt, since `PUT /tasks` is all-or-nothing and a silent failure used to lose everything since on the next reload (see its own comment); and except the couple of genuine awaited reads (`loadTasks()` inside `startApp()`, `getMe()` inside `boot()`/the login handler) that the rest of a page load depends on. One large file with heavy comments explaining *why*, not what — read the comments before changing behavior near timers, dismissal, or the recurrence split logic; the invariants are non-obvious and are explained inline rather than in a design doc.
- **`sharedInputBehavior.js`** — document-delegated focus/click/double-click text-selection behavior for every text `<input>`/`<textarea>` on the page, including ones created dynamically by modals. Self-contained IIFE, no exports.

**The marketing/subscription flow** — separate static pages, own stylesheet (`landing.css`, deliberately not `style.css`: that one assumes the app's fixed-viewport, no-page-scroll SPA layout, which would break these pages' normal scrolling), own EN/HR i18n (`site-i18n.js`) entirely separate from `app.js`'s own i18n system (different storage, different dictionary shape — see below):

- **`site-i18n.js`** — this flow's language handling: `resolveInitialSiteLanguage()` (a `?lang=` URL handoff, else a stored preference, else IP geolocation, same country-code rule as `app.js`'s own detection), `applySiteTranslations()` (a `data-i18n`/`data-i18n-html` sweep, same split as `app.js`'s `applyStaticTranslations`), and `initSitePage(dict, onLanguageChange?)` that every other page in this flow calls once with its own `{ en: {...}, hr: {...} }` dictionary. Also auto-updates every `a.js-login-link`'s `?lang=` query param on each render, so a link into `index.html` (the login/register screen, which has its own separate i18n) opens in the same language — see `boot()`'s own handling of that param in `app.js`.
- **`landing.html`**/**`landing.js`** — video + feature/pricing marketing page. Its pricing buttons check `getCurrentUserIdFromStoredToken()` (`auth.js`): logged in goes straight to `checkout.html?plan=...`, logged out goes to `index.html?next=checkout&plan=...&lang=...` first (see `app.js`'s login-form submit handler and `boot()`, both of which continue on to checkout right after if `next` is set).
- **`checkout.html`**/**`checkout.js`** — creates a real Stripe Checkout session server-side (`POST /subscriptions/checkout-sessions`) and redirects the browser to Stripe's own hosted page. This same page is also where Stripe redirects back once the visitor finishes (`successUrl` points here, with a `?session_id=...` Stripe substitutes in): `pollCheckoutSessionStatus()` then polls `GET /subscriptions/checkout-sessions/{sessionId}` until the backend's own (webhook-driven) confirmation catches up, before finally forwarding on to `success.html`. `cancelUrl` points straight at `cancel.html` instead, since there's nothing to confirm on a cancelled payment.
- **`success.html`**/**`success.js`**, **`cancel.html`**/**`cancel.js`** — Stripe's `success_url`/`cancel_url` final redirect targets; only `site-i18n.js` for logic, nothing else to do once there (the actual payment confirmation already happened in `checkout.js`, above).
- **`privacy.html`**/**`privacy.js`**, **`terms.html`**/**`terms.js`** — the Privacy Policy/Terms of Service, one `data-i18n-html` key per numbered section (heading + body together) rather than per-sentence, since that's far easier to keep aligned between languages for a document this size. Linked from the footer of every page in this flow, from below the login/register form on `index.html` (`.auth-legal-links`), and from the account menu once logged into the app (see `menu-item`s in `index.html`'s `#user-menu-dropdown`, right before Log out) — all three entry points are meant to open in whichever language is currently active where the link was clicked from (see `site-i18n.js`'s comment and `app.js`'s `updateOutboundLegalLinks`).

**`api-spec.yaml`** — the OpenAPI 3.0.3 contract every one of the above talks to (`/atodo/v1`, see Configuration for `apiBaseUrl`). Authoritative for request/response shapes, error `code`s, and the invariants that only make sense server-side (12-month-inactivity/scheduled-deletion enforcement, subscription-claim token re-issuing, ...) — read it, not just `auth.js`, when the client's behavior around auth/tasks/subscriptions is unclear. Not implemented anywhere in this repo; treat it as the spec a separate backend project must satisfy.

### Key domain concepts (in `app.js`)

- **Task vs. Occurrence**: a `Task` (`{ id, taskId, seriesId, name, description, details, dueDate, dueTime, allDay, appointment, passive, recurUntilCompleted, endDate, frequency, createdAt, log, comments }`) is a recurrence *pattern* — it holds no per-occurrence state at all. An `Occurrence` (`{ id, taskId, occurrenceDate, pendingReschedules, status, resolvedAt, dismissed, manual, overrides, comments, log, focusedSeconds, timerSeconds, timer }`) is one interacted-with instance of a task, addressed by `(taskId, occurrenceDate)` — sparse: a pattern-predicted date with nothing recorded against it (still pending, no note, no timer) has no row at all. Both arrays are fetched/saved as one unit (`GET`/`PUT /tasks`, see `loadTasks`/`saveTasks`) — there's no granular per-task/per-occurrence endpoint, since every mutation already computes the resulting full state locally before saving. `frequency` shapes are documented at the top of `recurrence.js` (`once`/`days`/`weeks`/`months`, with weekly weekday lists and several monthly day-selection modes).
  This split exists because occurrences used to be sparse maps (`completions`/`dismissed`/`markedFailed`/`pendingReschedules`) hung directly on the Task record, keyed loosely by date string — editing a task's pattern fields never invalidated them, so an edit could silently resurrect or corrupt a totally different occurrence's recorded state (most visibly for `recurUntilCompleted`, whose `dueDate` doubled as a live mutable "current occurrence" pointer). Every occurrence now has real identity and its own lifecycle instead.
  `app.js` keys almost everything off `task`/`occurrence` object references it already has in hand, via two chokepoints: `findOccurrence(task, occurrenceDate)` / `ensureOccurrence(task, occurrenceDate)` (find-or-create). For an ordinary task this is an exact `(taskId, occurrenceDate)` lookup; for a `recurUntilCompleted` task, an exact match is tried first (so re-deriving "the same occurrence" after changing its own status, e.g. to log an event right after marking it done, still finds it — looking up by "the current pending one" alone would stop working the instant status changes and mint a duplicate row), falling back to chain membership (`pendingReschedules`) only when nothing exists at that exact date yet.
- **Overdue vs. failed**: a normal task that's missed becomes "overdue" and carries over; a task flagged `appointment` becomes "failed" (permanent, crossed out red) instead once past due — see `pastDueStatus()`.
- **Dismissal**: `Occurrence.dismissed` is a boolean independent of `Occurrence.status` — not a third status value, a second axis. An occurrence can be `'completed'`/`'failed'` and not yet dismissed (the brief linger before it visually disappears — `scheduleDismissal`, ~5s, so the checkmark is visible first), or still `'pending'` and already dismissed (a genuinely missed occurrence swept off the list without ever being resolved — `markOccurrencesDismissedBefore`/`autoDismissStaleCarriedOverOccurrences`).
- **`recurUntilCompleted`**: such a task keeps at most one `'pending'` Occurrence alive at a time — its current, unresolved occurrence. Missing its due date pushes it forward one day at a time into its own `pendingReschedules` (`advanceRecurUntilCompletedTasks`/`Recurrence.advanceRecurUntilCompletedChain`) rather than going overdue/failed. Completing it (`resolveRecurUntilCompletedOccurrence`) marks that Occurrence `'completed'` and creates a **new** `'pending'` Occurrence for the next cycle (`Recurrence.nextRecurUntilCompletedDueDate`, re-anchored at the real completion date). Unchecking it again (`reopenRecurUntilCompletedOccurrence`) takes that next-cycle Occurrence back, moving anything already recorded on it onto the reopened one — refused once a later cycle has itself been resolved, since that would leave two live pending occurrences. `Task.dueDate` is only ever the date such a task was first created with — frozen from then on; the live current due date always lives on the pending Occurrence instead (`Occurrence.effectiveDueDate`).
- **Active task / timers**: only one task can be "active" at a time (`activeTaskId`/`activeOccurrenceDate`, fields on the account's own `User` resource server-side, persisted via a fire-and-forget `PATCH /users/me` in `saveActiveTaskId`), always changed through `setActiveTaskId()` so a timer's running/paused state is checkpointed consistently. The timer itself lives on the specific Occurrence being timed (`Occurrence.timer`) — a timer's remaining time is derived from a fixed checkpoint plus elapsed wall-clock time (`currentTimerRemaining`), not a live countdown, so it survives page reloads without drift.
- **Recurring task edits/deletes**: double-clicking a recurring occurrence prompts for scope (`showEditScopeChoice`: this occurrence / this and following / all). `'instance'` no longer splits the series into a new task record — it just writes `overrides` (name/description/details/dueTime/allDay/appointment/passive) onto that one Occurrence row, applied at render time via `Occurrence.applyOverrides` (see `buildTodoItemRow`/`showTodoContextMenu`'s own `effectiveTask`). `'following'` still forks a new Task record carrying the edited pattern forward (same `taskId`) — see the comments on `applySplitEdit`/`applySplitDelete`.
- **Notes and activity log, task-level vs. occurrence-level**: `Task.comments`/`Task.log` are general, not tied to one date (added while the side panel is scoped to `'task'`/`'series'`); `Occurrence.comments`/`Occurrence.log` are scoped to one specific date (`'occurrence'` scope) — see `addTaskComment`/`addOccurrenceComment` and `logTaskEvent`/`logOccurrenceEvent`. The side panel's occurrence/task/series toggle (`sidePanelScope`) reflects this: `'occurrence'` shows only the selected Occurrence's own comments/log; `'task'`/`'series'` union every in-scope Task record's own comments/log with every Occurrence row's for those taskIds (see `renderSidePanel`).
- **Three list views**, cycled via one toggle button and persisted separately from the underlying overdue/active computations (view mode is a display preference only, also a `User` field — see `todoViewMode`/`saveTodoViewMode`): "pending/overdue" (`computeTodoDisplayItems`) shows every overdue/failed occurrence since the start of the current calendar month plus today/tomorrow, ignoring `Occurrence.dismissed`; "next recurrence" (`computeNextRecurrenceItems`) is the day-to-day decluttered view that respects dismissal; "all tasks" (`computeAllTasksItems`) lists every occurrence in the current calendar month regardless of state.
- **Subscriptions & free-tier limits**: a free/lapsed account is capped at `FREE_TASK_LIMITS.once`/`.recurring` tasks and `NOTES_PER_TASK_LIMIT` notes per task, counted by `task.taskId` (not `task.id`, which changes across a recurring split — see `unlockedTaskIds`/`canCompleteOrNoteTask`); notes are pooled across a taskId's Task-level *and* Occurrence-level comments together (`notesUsedFor`/`Occurrence.notesCount`). A lapsed subscription keeps every task/note but only grandfathers the first ones ever created (by `task.createdAt`); a task beyond that shows a padlock in place of its checkbox/Add note button/Manage Tasks row instead. Free/lapsed accounts also get a permanent, unremovable `SUBSCRIPTION_PROMPT_TASK_ID` task (see `ensureSubscriptionPromptTask`/`isProtectedTask`). The bearer token embeds a subscription snapshot (see the `Token` schema in `api-spec.yaml`) so limit checks read from the token rather than a freely-editable place; `subscribeCurrentUserToTrial`/`cancelCurrentUserSubscription`/etc. in `app.js` replace it with the fresh one every subscription-mutating endpoint re-issues.
- **Account deletion & inactivity**: a user can permanently delete their own account from Settings' danger zone (`deleteCurrentUserAccount`, `DELETE /users/me` — deletes the account and every task/note/preference tied to it, enforced server-side); an account untouched for 12 months, or one whose scheduled deletion (`POST /users/me/schedule-deletion`) has come due, is deleted automatically instead, per the Privacy Policy — both enforced by the backend, not this client, at `POST /auth/login`/`GET /auth/me` time (see api-spec.yaml's own notes on those endpoints and `lastActiveAt`/`lastLoginAt`). `getMe()` is the one chokepoint both `boot()`'s existing-token path and a fresh `login()` always call through, so a stale/deleted account can't slip past either entry point (see `getMe`'s own comment for why) and `describeAuthError()` maps the resulting `ACCOUNT_EXPIRED_INACTIVITY`/`ACCOUNT_DELETED_SCHEDULED`/`NETWORK_ERROR` codes to a translated message.
