# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A to-do list web app (recurring tasks, overdue/failed states, work timers), ported out of the `browser` project's new-tab widget. Plain HTML/CSS/JS, no build step, no framework, no package.json. Multi-tenant: every account's tasks/profile/subscription live server-side behind a real HTTP backend, not in `localStorage` — see `api-spec.yaml` for the full contract and Architecture below for how the client talks to it. So do the to-do list's rules (recurrence, overdue/failed, carried-over occurrences, timers, the free plan's limits): the client reads what it shows — one local day of the list at a time — and sends one action request per change. `localStorage` is only used client-side now for the bearer token itself and (briefly, pre-login) marketing-language/config values. Also includes a marketing/subscription flow (`landing.html` and friends, see Architecture) alongside the app itself.

There is no backend implementation in this repository — `api-spec.yaml` is the contract the sibling `male-niti-api` project implements (its `lib/atodo/domain/` holds the task rules, with their tests); this repo is just the client.

## Commands

- **Run the app**: needs a backend implementing `api-spec.yaml` reachable at the configured `apiBaseUrl` (see Configuration below) — open `index.html` directly in a browser, or serve the directory (e.g. `npx serve .`), either way there's no dev server or build step for the client itself.
- **Tests**: none in this repo. The task rules (recurrence, occurrences, views, actions) moved to the backend along with their tests (`male-niti-api`'s `npm test`); the client (`app.js`, `auth.js`, `checkout.js`, ...) has no automated coverage — verify changes by hand against a running backend.
- **Docker**: `docker build .` copies the static files (see the two `COPY` lines in `Dockerfile` — the main app's scripts, and the landing/checkout/success/cancel pages) into an `nginx:alpine` image. If you add a new source file, add it to one of those `COPY` lines too, or it won't ship. `config.js` is the one deliberate exception — see Configuration below. The favicons (`favicon.ico`/`favicon.svg`/`apple-touch-icon.png`, linked from every page's `<head>`) and `logo-on-dark.svg` (`landing.html`'s header) are COPYed too; their sources, the logos and the Stripe branding uploads live in `brand/` (not shipped — see its README). `nginx.conf` replaces the image's stock `default.conf` only to add `Cache-Control: no-cache`, so a redeploy is picked up on the next plain reload rather than a hard reload (see its own comment for why stale client code matters here). `./atd <port>` builds and (re)runs the image via Docker — one image and container per port (`advanced-todo:<port>`, `advanced-todo-<port>`), so builds of different checkouts (e.g. branches via `git worktree`) can run side by side; it requires a `.env` file in this directory (refuses to start without one) and sources it with `set -a` before `docker run`, so anything in `.env` (`UNSPLASH_ACCESS_KEY`, `LANDING_VIDEO_URL_EN`, `LANDING_VIDEO_URL_HR`, `API_BASE_URL`) is forwarded into the container as an env var. This container only ever serves the static client — the backend is a separate deployment.

## Configuration

Four configurable values so far, all loaded from `window.APP_CONFIG` set in `config.js`. There's no build step, so this is a plain untracked (gitignored) JS file, not an env-driven bundler define:

- `apiBaseUrl`, the backend implementing `api-spec.yaml` (e.g. `https://api.example.com`) — `auth.js`'s `apiFetch` prefixes every request with `${apiBaseUrl}/atodo/v1`. Left empty, requests go to a same-origin `/atodo/v1`, which only works if the backend happens to be reverse-proxied onto this same origin.
- An app-wide Unsplash Access Key (used by the background picker in Settings — see `app.js`'s `configuredUnsplashAccessKey`/`loadUnsplashAccessKey`).
- `landingVideoUrlEn`/`landingVideoUrlHr`, YouTube links for `landing.html`'s walkthrough video — one per language, since each is a separate recording rather than one video with translated captions (see `landing.js`'s `setUpVideo`, which re-picks and re-embeds on load and on every EN/HR toggle click via `site-i18n.js`'s `initSitePage`, and `toYouTubeEmbedUrl`, which accepts a plain watch URL, a `youtu.be` short link, or an already-embeddable one). Either left empty independently, that language just shows a placeholder instead.

- **Local dev**: copy `config.example.js` to `config.js` and fill in real values (get an Unsplash key at https://unsplash.com/developers). `index.html`/`landing.html`/`checkout.html` (every page that calls the API) load `config.js` before their other scripts; it's fine to skip this file entirely (`config.js` 404s harmlessly, `window.APP_CONFIG` stays undefined) — `apiBaseUrl` then falls back to a same-origin `/atodo/v1`, the background picker falls back to asking each user to paste in their own key (stored per-device in `localStorage`), and the landing page just shows its video placeholder regardless of language.
- **Docker (via `./atd`)**: don't create `config.js` yourself — put `UNSPLASH_ACCESS_KEY=...`/`LANDING_VIDEO_URL_EN=...`/`LANDING_VIDEO_URL_HR=...`/`API_BASE_URL=...` in a gitignored `.env` file next to `Dockerfile` instead. `./atd` sources it and forwards all four into the container; `docker-entrypoint.d/40-write-app-config.sh` (nginx:alpine's image runs every `*.sh` in `/docker-entrypoint.d/` on container start) then generates `config.js` fresh from those env vars every time the container starts, so any of them can be rotated by editing `.env` and re-running `./atd`, no rebuild needed.

## Architecture

Two independent halves sharing one origin (and so one `localStorage`, used now only for the bearer token and a couple of pre-login display preferences — see Configuration/`site-i18n.js` below): the to-do app itself (`index.html`), and a marketing/subscription/legal/help flow (`landing.html`, `checkout.html`, `success.html`, `cancel.html`, `privacy.html`, `terms.html`, `faq.html`, `support.html`) that isn't part of that SPA and never loads `app.js` (which assumes `index.html`'s own DOM exists and would throw trying to query it elsewhere). Both halves talk to the same backend (`api-spec.yaml`, `/atodo/v1`) via `auth.js`. No modules, no bundler anywhere — load order matters and everything each page loads is global.

**The app** — scripts loaded via plain `<script>` tags in this order (`index.html`): `config.js` (see Configuration), `version.js`, `sharedInputBehavior.js`, `dates.js`, `auth.js`, `anchor-prices.js`, `app.js`.

- **`dates.js`** — `Dates`: plain calendar helpers (`dateToISO`, `addDays`, `shiftISO`, `daysInMonth`, `todayISO`) and the browser's IANA time zone (`timeZone()`). No rules — what a task does on which day is the server's business.
- **`auth.js`** — the API client. `apiFetch(path, { method, body, token })` is the one place every request to the backend goes through: prefixes `path` with `apiBaseUrl` + `/atodo/v1` (see Configuration), sends the browser's time zone as `X-Timezone` (the server works out "today" and due times in it), attaches the bearer token from `localStorage` (or an explicitly-passed one, for a token that isn't stored yet — see `getMe`'s own call sites in `app.js`), waits and retries a read the server rate-limited (429, `RateLimit-Reset`), and turns any non-2xx response into a `codeError(code, message)` so the rest of the app can branch on a stable `err.code` the same way regardless of which endpoint failed. Everything else here is a thin wrapper around one `api-spec.yaml` endpoint (`startTrialSubscription`, `createCheckoutSession`/`getCheckoutSessionStatus`, `createBillingPortalSession` — Settings' "Manage billing", Stripe's hosted Customer Portal — `cancelSubscription`, `scheduleAccountDeletion`/`cancelScheduledAccountDeletion`) plus `decodeToken()`/`describeSubscription()` (non-authoritative local reads of a token's claims, for instant UI decisions that don't need a round trip), and `getCurrentUserIdFromStoredToken()`. Pulled out of `app.js` specifically so `landing.html`/`checkout.html` can use the same API client without loading the whole SPA script. No DOM beyond `localStorage`.
- **`app.js`** — everything else: the to-do list's loading and rendering, the side panel and agenda, timers' display, the generic `showFormModal()` used for all add/edit forms (a `window.prompt()`/native-dialog replacement, since Linux Chromium has no OS text-input dialog), the tabbed task editor (`openTaskEditor`), Manage Tasks, stats, Settings. It holds no task rules: lists come from the server as `Item`s that carry what a row shows and which `actions` it allows, and every change is one action request through `runAction` (see Key domain concepts). One large file with comments explaining *why*, not what — read them before changing behavior near the list's loading/scrolling, the day highlight, or timers.
- **`sharedInputBehavior.js`** — document-delegated focus/click/double-click text-selection behavior for every text `<input>`/`<textarea>` on the page, including ones created dynamically by modals. Self-contained IIFE, no exports.

**The marketing/subscription flow** — separate static pages, own stylesheet (`landing.css`, deliberately not `style.css`: that one assumes the app's fixed-viewport, no-page-scroll SPA layout, which would break these pages' normal scrolling), own EN/HR i18n (`site-i18n.js`) entirely separate from `app.js`'s own i18n system (different storage, different dictionary shape — see below):

- **`site-i18n.js`** — this flow's language handling: `resolveInitialSiteLanguage()` (a `?lang=` URL handoff, else a stored preference, else IP geolocation, same country-code rule as `app.js`'s own detection), `applySiteTranslations()` (a `data-i18n`/`data-i18n-html` sweep, same split as `app.js`'s `applyStaticTranslations`), and `initSitePage(dict, onLanguageChange?)` that every other page in this flow calls once with its own `{ en: {...}, hr: {...} }` dictionary. Also auto-updates every `a.js-login-link`'s `?lang=` query param on each render, so a link into `index.html` (the login/register screen, which has its own separate i18n) opens in the same language — see `boot()`'s own handling of that param in `app.js`.
- **`landing.html`**/**`landing.js`** — video + feature/pricing marketing page. The pricing cards are the brand's products from the price list (`renderPricingCards`): those with `featured_ord`, in that order, `highlight` outlined, with their names and prices — a free product (no billing interval) lists the free limits and leads to sign-up, a subscription Pro's benefits and checkout for its plan. Below the pricing cards it offers the published price list (CSV) for download, every version still due listed oldest first (`loadPriceListVersions` — from the API's `/maleniti/v1/price-lists/atodo/versions`, not `/atodo/v1`, so plain `fetch` on `apiBaseUrl` rather than `apiFetch`; the platform proxies that path on atodo.maleniti.com too). Its pricing buttons check `getCurrentUserIdFromStoredToken()` (`auth.js`): logged in goes straight to `checkout.html?plan=...`, logged out goes to `index.html?next=checkout&plan=...&lang=...` first, which opens on registration rather than login for such a visitor (most have no account yet). The plan travels with the registration (`registerUser`'s `checkoutPlan`), so the emailed verification link carries `next=checkout&plan=...` too — and verifying logs the new account in (for everyone, see `handleEmailVerificationLink`, which `boot()` awaits before anything else signs in). Every way into a session goes through `enterSession`: on to checkout when `checkoutPlanFromUrl()` says the visitor came to subscribe, into the app otherwise. Registering with an email that's already an account (`showEmailTakenMessage`, the same for every visitor) offers a "log in" link that tries the email and password just entered (`logInWith`), else quietly switches to the login screen with the email filled in.
- **`checkout.html`**/**`checkout.js`** — creates a real Stripe Checkout session server-side (`POST /subscriptions/checkout-sessions`) and redirects the browser to Stripe's own hosted page. This same page is also where Stripe redirects back once the visitor finishes (`successUrl` points here, with a `?session_id=...` Stripe substitutes in): `pollCheckoutSessionStatus()` then polls `GET /subscriptions/checkout-sessions/{sessionId}` until the backend's own (webhook-driven) confirmation catches up, before finally forwarding on to `success.html`. `cancelUrl` points straight at `cancel.html` instead, since there's nothing to confirm on a cancelled payment. The backend refuses checkout (503 `PAYMENTS_UNAVAILABLE`) whenever it can't fiscalize payments (Croatian B2C fiscalization, done entirely server-side), 409 `ALREADY_SUBSCRIBED` for an active subscriber, and 409 `SUBSCRIPTION_CANCELLING` for a cancelled subscription whose paid period still runs (a second one would charge again for time already paid for) -- `checkout.js` passes these on to `cancel.html` as `?reason=unavailable|subscribed|resumable`, which swaps in a matching explanation: a subscriber gets "Go to my to-do list" instead of "Back to pricing", and `resumable` also offers "Resume subscription" (`resumeSubscription`, `POST /subscriptions/resume`: renews again at the period's end, nothing charged now -- also in Settings, `resumeCurrentUserSubscription`).
- **`success.html`**/**`success.js`**, **`cancel.html`**/**`cancel.js`** — Stripe's `success_url`/`cancel_url` final redirect targets; only `site-i18n.js` for logic, nothing else to do once there (the actual payment confirmation already happened in `checkout.js`, above).
- **`support.html`**/**`support.js`** — the support form (billing, account, bug, feature, complaint, other — `?topic=` preselects one): `POST /atodo/v1/support` through `apiFetch`, so a logged-in visitor's message goes out from their account (name and email prefilled), with the client's version (`version.js`), page, language and browser for diagnosis; works logged out too. **`faq.html`**/**`faq.js`** — the FAQ, one `data-i18n-html` `<details>` per question, linking to the support form (and it back). Both linked from the avatar menu (after Terms of Service), below the login/register forms and in every page's footer; keep the FAQ's answers true to how the app behaves (its button names, limits, link lifetimes).
- **`privacy.html`**/**`privacy.js`**, **`terms.html`**/**`terms.js`** — the Privacy Policy/Terms of Service, one `data-i18n-html` key per numbered section (heading + body together) rather than per-sentence, since that's far easier to keep aligned between languages for a document this size. Linked from the footer of every page in this flow, from below the login/register form on `index.html` (`.auth-legal-links`), and from the account menu once logged into the app (see `menu-item`s in `index.html`'s `#user-menu-dropdown`, right before Log out) — all three entry points are meant to open in whichever language is currently active where the link was clicked from (see `site-i18n.js`'s comment and `app.js`'s `updateOutboundLegalLinks`).

**`anchor-prices.js`** — shared by both halves (`index.html`, `landing.html`, `checkout.html`): every price the site shows comes from the published price list — the API's `GET /maleniti/v1/price-lists/atodo/current` (`loadSitePrices`, once per page and language), the same prices checkout charges; no amount is hardcoded anywhere in the client. Croatian law (NN 101/2026, from 17 Nov 2026) also requires every price shown to consumers to carry its anchor price ("sidrena cijena"). A page marks a price's place with an empty `<span data-price-plan="monthly">` and its badge with `<span data-anchor-plan="monthly">` (also inside translated strings; plans are named by billing interval, `monthly`/`annual`) and calls `fillAnchorPrices(root, lang)` after every (re)translation; placeholders fill as soon as the prices arrive ("—" if they can't load). A badge is an anchor icon, the amount and a CSS tooltip (`.anchor-price`, duplicated in `style.css` and `landing.css`) saying why it's there, plus that it isn't the price you pay once the two differ. Stripe's Checkout page gets the same from the backend. A new place showing a price uses these placeholders too.

**`api-spec.yaml`** — the OpenAPI 3.0.3 contract every one of the above talks to (`/atodo/v1`, see Configuration for `apiBaseUrl`). Authoritative for request/response shapes, error `code`s, and the invariants that only make sense server-side (12-month-inactivity/scheduled-deletion enforcement, subscription-claim token re-issuing, ...) — read it, not just `auth.js`, when the client's behavior around auth/tasks/subscriptions is unclear. Not implemented anywhere in this repo; treat it as the spec a separate backend project must satisfy.

### Key domain concepts

The rules themselves live in the backend (`male-niti-api`'s `lib/atodo/domain/`, with its own comments and tests) and `api-spec.yaml` documents what each endpoint does; what the client needs to know:

- **Task vs. Occurrence** (server-side): a `Task` is one record per task — its data plus its *current* recurrence pattern (no history of earlier patterns). An `Occurrence` is one interacted-with instance, addressed by `(taskId, occurrenceDate)` — sparse: a pattern date with nothing recorded has no row, and every row always counts as an occurrence whatever the pattern says. A pattern change applies from today on (earlier dates are saved as rows first); `frequency` shapes are documented in the backend's `recurrence.js` and the spec's `Frequency`. The client never handles these raw — only in the import/export file.
- **Overdue vs. failed**: a missed normal task becomes "overdue" and carries over; an `appointment` becomes "failed" (permanent, crossed out) once past due — it can still be focused and timed, and doesn't count as failed while focused; a `passive` task's checkbox marks it failed rather than done, and a timed one counts as done once its due time has passed (derived server-side, `isPassiveDoneByTime` — after its time it's done or failed, before it pending or failed; an all-day one carries over until marked failed or dismissed). **Dismissal** (`Item.dismissed`) is a second axis next to the status: a carried-over occurrence can be hidden without being resolved (the row's ✕, `dismiss`/`restore`), and the server sweeps stale ones and dismisses a completed task's earlier missed occurrences.
- **`recurUntilCompleted`**: keeps one live pending occurrence, pushed forward a day at a time while missed rather than going overdue; completing it starts the next cycle, reopening takes that back (refused once a later cycle was resolved — `REOPEN_BLOCKED`).
- **The list's data** (`resetTodoList`/`fillTodoList`/`refreshTodoList`, `GET /days`): one local day at a time — the items a view shows that day, or the nearest day with items, plus the nearest days either side. The list starts at today (or the 1st of another month) and loads days until the view is filled with a margin, more as it scrolls either way, within the viewed month ("next recurrence" isn't month-bound). Every loaded day is kept (`todoDays`) until the view or month changes, so the list never shrinks under the reader; a kept day is fetched again when it's on screen and its copy is over `TODO_DAY_FRESH_MS` old (or an action may have changed it, or the tab comes back into view) — `refreshVisibleTodoDays`/`walkTodoSpan`, which walk day by day so a day that emptied drops out and one that gained items appears. A redraw keeps the first day on screen in place (`todoScrollAnchor`). Only the Today button may start the list over (today, in the viewed range, not loaded).
- **Items and actions** (`buildTodoItemRow`, `showTodoContextMenu`): a row draws exactly what its `Item` says — `label` ("series: name" in a mixed series), `dueTime` in local time with `zoneDueTime` for a task fixed to another zone ("Due 15:00 · 09:00 New York"), `locked` (a padlock), `timer` — and offers exactly its `actions` (`TODO_ITEM_ACTIONS` maps each to a menu entry). The subscription reminder a free account sees on today is an item with `virtual: 'subscription-prompt'`, worded by the client.
- **Actions** (`runAction`, `occurrenceAction`, `taskAction`): every change is one request, run one at a time in order. A request that fails for a reason that will pass (`NETWORK_ERROR`, `MAINTENANCE`) stays queued behind the save-status banner (`renderSaveStatus`, retried automatically or from the banner, and leaving the page asks first); one the server refuses is reported (`reportActionError`: a free-plan limit — `TASK_LIMIT`/`NOTE_LIMIT`/`TASK_LOCKED` — offers a subscription, a few codes have their own wording, anything else shows the server's message) and dropped. After an action, `refreshEverything` re-fetches the list's visible days, the side panel and Manage Tasks; checking an item off shows it checked at once and keeps it ~5 s before re-fetching (`resolveItem`, `linger`), so the checkmark is seen before it may go.
- **Focus & timers**: only one occurrence is focused at a time (`PUT`/`DELETE /focus` — "Work on this now", or resuming/pausing its timer); the server checkpoints the previous one's timer or focus time. A timer lives on its occurrence (`Item.timer`): remaining time is derived from a checkpoint plus elapsed wall-clock time (`currentTimerRemaining`), so the list just redraws once a second while one runs (`ensureTimerTicking`). A recurring task measured at least once also offers "Auto timer (16m 12s)": a countdown of its average measured time over every measured occurrence (`Item.autoTimerSeconds`, the agenda's block length too), started at once (`POST …/timer` with `auto: true`). Expiry is the server's: when a countdown reaches zero (or any timer the 360-minute cap) the client re-fetches, and any response's `expiredTimers` plays the chime. While the row with a running timer isn't on screen (scrolled away, or its day not loaded — another month or view), the toolbar shows it (`#todo-timer-chip`, `updateTodoTimerChip`: its name and timer as on the row, left of the month and view controls; on its own line below them on narrow screens); a click scrolls to the row, loading days or switching month first (`revealTodoItem`). The focused occurrence comes with every day and agenda read (`focused`, kept in `focusedTodoItem`), so it's known wherever it is.
- **Time zones**: every request carries the browser's zone (`X-Timezone`), and every date and time shown or sent is local. A timed task can be fixed to a zone (the editor's "Time zone" field, "Fluid" by default — `timeZoneFieldSpec`): it then occurs on its zone's dates and is due at that moment, shown on the local day of it. All-day tasks have no zone.
- **Editing a task**: one modal, three tabs (`openTaskEditor`, built on `showFormModal`'s `opts.tabs`, on `GET /tasks/:taskId`): **Details** (name/description/details/time/zone/flags — every occurrence, past and future; `PATCH /tasks/:taskId`), **Recurrence** (the pattern, from today on; `PUT /tasks/:taskId/pattern` — sent first, and refused, nothing of the edit is saved), and **Occurrences** (`renderOccurrencesTab`: the server's `occurrenceList` — every past occurrence plus the next one, and the one after if the next is done; select one to edit its own details and notes or delete it, add an extra occurrence on any date (`promptManualOccurrence`), or pull an upcoming pattern date in to edit ahead (`promptFindOccurrence`, its calendar limited to the pattern's dates from `GET /tasks/:taskId/dates`); these apply immediately, not on Save). Double-click, the context menu's "Edit" and Manage Tasks' edit button open Details; the side panel's "Edit this occurrence…" opens Occurrences with that occurrence selected. Adding a task uses the plain `openTaskForm`.
- **Pausing recurrence**: the context menu's "Pause recurrence until…" (`promptPauseRecurrence`, on `showDatePickerModal`'s month grid): every occurrence from the right-clicked one up to the picked date is hidden, recurrence resumes on exactly that date (`POST /tasks/:taskId/pause`). While a pause is in effect, "Resume recurrence now" restarts it today (`resume`).
- **Side panel & agenda** (`selectTaskForSidePanel`, `refreshSidePanel`, `renderSidePanel`): notes and activity for the selected task, scoped to the one occurrence, the task, or its whole series (`sidePanelScope` — `GET /tasks/:taskId`, and `GET /series/:seriesId?notes=1` for series scope); notes are task-level or occurrence-level by scope. With nothing selected it shows today's agenda (`GET /agenda`): timed tasks sized by how long they usually take, draggable to a new time (`PUT /tasks/:taskId/due-time`, local time). It also draws every focus/timer session of the day where it ran (`sessions`, `buildAgendaSessionBlock`): fixed outlined frames, a clock icon on timed ones, the running one dashed and growing with the clock (`positionAgendaNowLine` redraws). An occurrence measured that day loses its due-time block — its sessions stand in for it, with its menu and double-click; right-click/long press on a stored one also offers "Delete this measurement" (`DELETE /focus-sessions/:id`, which takes its time off the stats too). Ctrl + mouse wheel (or a trackpad pinch) and a two-finger pinch zoom the agenda vertically around the pointer (`zoomAgenda`: 22–600 px per hour, half/quarter-hour lines once there's room, remembered per device in `localStorage`); `touch-action: pan-y` keeps the browser from zooming the page instead.
- **Day highlight**: the list highlights (undimmed, the rest `.not-today`) the day being read, not just today (`updateTodoDayHighlight`, on scroll/resize/render) — by progress through the day with hysteresis. The reading point is the middle of a preferred band 20–35 % down the visible list (`todoReadingGeometry`; near the very top of the list the band rides up with the scroll, so the first day is highlighted there with no empty space above it). The highlight moves on once progress through the current day passes a height-dependent threshold (`switchThreshold`: 65 % for a short day down to 45 % for one as tall as the list) and the next day's top is inside or just below the band; it moves back once the current day's top drops below the band plus a gap (`BACK_GAP`). Days are separated by a plain line (`.todo-day-divider`); there are no day headers. The highlighted day is named by the page title instead (`renderAppTitle`: "Pending and overdue tasks for" / "Upcoming tasks for" / "All tasks for" plus the day's name, the day on its own line on narrow screens), with a "+" (a task due that day) and, whenever it isn't today, a "Today" button next to it — `scrollTodoToToday` puts today's top, or the first later day's, at the reading point; while another month is browsed it's always there and goes back to the current month instead, `jumpTodoToCurrentMonth`, same as clicking the month label. A day the list jumps to itself (`scrollTodoToDay`: Today, opening on today) is highlighted at once and pinned until the scroll ends (`todoPinnedDate`), so the hysteresis can't stop short of it. Every other day fades with its distance from the reading point — those days' rows trade the glass backdrop-filter for a plain translucent background, since a backdrop-filter snaps rather than fades with opacity. Page Down/Space and Page Up/Shift+Space step the highlight one day at a time (the keydown handler next to `scrollTodoToDay`; stepping back scrolls just far enough past the hysteresis gap). A spacer after the last day (`sizeTodoListSpacers`) lets a short last day reach the band. The list opens on today on the first render and after switching view or month (`todoScrollToTodayOnRender`).
- **Three list views**, cycled via one toggle button, computed server-side (`GET /days?view=`) and persisted as a `User` field (`todoViewMode`/`saveTodoViewMode`): "pending/overdue" (every overdue/failed occurrence since the start of the month, dismissed or not, plus today/tomorrow), "next recurrence" (the day-to-day decluttered view, respecting dismissal), "all tasks" (every occurrence in the month).
- **Subscriptions & free-tier limits**: enforced server-side — a free/lapsed account has 10 one-off and 5 recurring tasks (creating one, or editing a task between the two kinds, past that is `TASK_LIMIT`) and 5 notes per task (task- and occurrence-level together, `NOTE_LIMIT`); a lapsed subscription keeps every task but only its first ones by creation stay usable, the rest `locked` (`TASK_LOCKED`) — a padlock in place of the checkbox, the side panel's "Add note" and Manage Tasks' row. A free trial is offered only while the server says so (`User.trialAvailable` → `currentUserTrialAvailable`: the account has never had any plan, counting before it was deleted and reopened; 409 `TRIAL_UNAVAILABLE`): anyone else gets "Subscribe…" in the same places (Settings, the paywall modal — `setI18nKey` swaps their labels), leading to `landing.html`'s pricing (`goToPricing`). The bearer token embeds a subscription snapshot (see the `Token` schema in `api-spec.yaml`); `subscribeCurrentUserToTrial`/`cancelCurrentUserSubscription`/etc. in `app.js` replace it with the fresh one every subscription-mutating endpoint re-issues.
- **Import & export** (Settings): "Download my data" saves the server's `GET /export`; "Import data" (`importUserData`) uploads a file in pieces of whole tasks with their occurrences (`splitImportIntoChunks`, ~256 KB each, at least 250 ms apart, `TOO_FAST` waited out) behind a progress bar with Cancel, then commits — the server replaces every task in one go, bringing older formats up to date and trimming a free account's import to its limits (`limited`). The confirmation shows the file's size, with a data-usage warning on a metered or data-saver connection (`isMeteredConnection`).
- **Changing the login email**: Settings' "Change email…" (`promptChangeEmail`, `POST /users/me/change-email`, current password required) doesn't change it yet -- the new address gets a 6h verification link, the old one a 30-day undo link (see api-spec.yaml's `/auth/verify-email-change`, `/auth/undo-email-change`, `/auth/reset-password`). `boot()` handles both links from the URL: `?verifyEmailChange=` like `?verify=` (not awaited), but `?undoEmailChange=` *before* anything signs in (`handleUndoEmailChangeLink` -- the undo ends every session), then straight into setting a new password (`openPasswordResetModal`, the change-password modal in reset mode), and every outcome reloads into a normal boot with a one-time notice (`reloadWithNotice`/`showPostBootNotice`).
- **Forgotten passwords**: the login screen's "Forgot password?" (`#forgot-password-link`) asks for the email and calls `POST /auth/forgot-password`, which answers the same whether or not it has an account. The emailed link (`?resetPassword=<token>`, valid 30 minutes, once) is handled by `boot()` before anything signs in (`handlePasswordResetLink`): the change-password modal in reset mode (`openPasswordResetModal({ kind: 'forgot', resetToken })`), then `POST /auth/reset-password`, which logs in (a deleted account comes back reopened — `restored` → `login.accountRestored`). A session the tab already has is left alone until the new password is actually set.
- **Stats**: one modal, three scopes (`showStatsModal`, `GET /stats?scope=`): a task (its context menu's "Task stats", `showTaskStatsModal`), a series (Manage Tasks' series pane, "Series stats") or all tasks (Manage Tasks, "Stats (all tasks)"). The series/all views add an overview (how many tasks, occurrences to date) and list time per day, each day's deletable (a bad measurement). "Reset stats…" (two clicks, `buildResetStatsButton`, `POST /stats/reset`) starts every task in scope over: measured time is cleared and completions and occurrences count only from then on. The task's history itself is never touched.
- **Updates & maintenance** (the platform deploys versioned releases, see `male-niti`'s `mn deploy`): while the backend is being updated, it (or nginx in front of it) answers 503 `MAINTENANCE` — `apiFetch` also maps a code-less 502/503/504 to it. Actions just stay queued: `renderSaveStatus` shows a calm "being updated" banner instead of "not saved" (same retries, see Actions above). `boot()`'s stored-token path (`resumeStoredSession`) keeps the session on `MAINTENANCE`/`NETWORK_ERROR` and retries every 15 s, rather than logging out — only an answer about the account itself ends it; checkout sends `MAINTENANCE` to `cancel.html?reason=unavailable`. `startSiteStatusPolling` (from `startApp`) reads the platform's `_status.json` (served by nginx, written by `mn`) every 5 minutes and on tab focus: an announced maintenance window, and the live `clientVersion` — differing from this tab's `window.APP_VERSION` (`version.js`, generated by the Dockerfile from build arg `VERSION`, `dev` by default and when opened locally without it) offers a reload (`renderSiteStatus`, `#site-status-banner`).
- **Account deletion & inactivity**: a user can delete their own account from Settings' danger zone (`deleteCurrentUserAccount`, `DELETE /users/me` — deletes every task/note/preference tied to it, enforced server-side). Deleting *closes* the account rather than erasing it: for 12 months the backend keeps only its email, password hash and trial status (Privacy Policy section 4), so the email stays taken (`EMAIL_TAKEN` on register/change-email) and logging in again reopens it empty — the login response's `restored: true`, on which the login handler shows `login.accountRestored`; an account untouched for 12 months, or one whose scheduled deletion (`POST /users/me/schedule-deletion`) has come due, is deleted automatically instead, per the Privacy Policy — both enforced by the backend, not this client, at `POST /auth/login`/`GET /auth/me` time (see api-spec.yaml's own notes on those endpoints and `lastActiveAt`/`lastLoginAt`). `getMe()` is the one chokepoint both `boot()`'s existing-token path and a fresh `login()` always call through, so a stale/deleted account can't slip past either entry point (see `getMe`'s own comment for why) and `describeAuthError()` maps the resulting `ACCOUNT_EXPIRED_INACTIVITY`/`ACCOUNT_DELETED_SCHEDULED`/`NETWORK_ERROR` codes to a translated message.
